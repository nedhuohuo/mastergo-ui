# L3 新旧规范 A/B 对照结果

## 方法

| 项 | 设置 |
|---|---|
| A 臂（旧） | `/tmp/mastergo-ui-skill-backup-20261011195346`（改前实际生效版：含形态识别、android-pitfalls，无五项分析门禁） |
| B 臂（新） | `.worktrees/mastergo-android-ui-workflow`（当前版：加五项分析门禁、模板、check-ui-analysis、文案与颜色新规则） |
| 输入 | 同一份 fixture：`output/ab/fixture-84-079220.md`（84:079220 的 5/17 个 section + 全量文案闭集） |
| 任务描述 | 两臂逐字相同，只换规范目录与产出路径；都停在「准备到可开工、不写代码」 |
| 执行 | 两个干净上下文子代理（`delegate`），同一模型，各自出 `arm-old.md` / `arm-new.md` |
| 耗时 | A 310s / B 535s |

## 限制（结论必须带着这些读）

1. 子代理不带 MasterGo MCP，数据只能落成文件 → 只覆盖 5/17 个 section，「是否读全 section」这类读取阶段指标本次量不到。
2. A 臂报告称它「顺带看了同 worktree 的模板与门禁脚本，未作为依据」——存在轻度污染，A 的产出比纯旧规范更规整。
3. n=1，随机性无法排除；差异明显处可信，细微处不能下结论。
4. fixture 未含底部两条固定层，因此「底部固定/滚动让位」一项两臂都无数据支撑，不是有效信号。
5. 两臂都未越界写代码（`git status` 只有产出文件，无 `.xml`/`.kt`）。

## 结论

1. **这次改动的可测效果集中在三处**：产出结构固定为模板五段（门禁 0 vs 1）、验收章节出现（adb/uiautomator 0 vs 3）、文案规则生效（`strings.xml` 5 vs 1，A 还专门写了 string key 附录）。
2. **抓坑能力没有提升**：五个坑两臂都抓到了。说明上一轮的「伪影判据 + 形态识别」已经在起作用，这次的增量不在这里。
3. **代价**：B 比 A 慢 72%（535s vs 310s），产出更短（266 vs 294 行）——换到的是**可判定、可汇总**的结构，而不是更多信息。
4. A 的产出更像一份自由散文（12 个自拟标题、7 处缺口/阻塞措辞），信息量不低但无法机器校验；B 的产出能被门禁脚本判 0/1。

## 建议

- 保留这次的改动：价值在于「能不能自动判定」，不在于「能不能抓到坑」。
- 抓坑能力已经不是瓶颈，别再往规范里加同类判据；下一段风险在代码阶段与真机验收，那里目前只有人工检查。
- 若要复跑：换一个两边都没见过的设计稿，并把 fixture 扩到全量 section；同时让 A 臂用独立副本目录，避免它读到新模板。
